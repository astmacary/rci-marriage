# January 2027 pilot

The browser uses the existing Microsoft registration and each signed-in person's SharePoint access. The private job, `node scripts/pilot-sync.cjs`, projects status and releases sealed notes. Run it with the app source and `src/data.js` on a private host. Browser hosting alone cannot run it.

1. Create a Pilot Intake list with a plain-text multiline AppData column. Give pilot spouses Contribute with author-only read and edit, and give the sync identity access to all intake. Keep leaders and existing reveal and mentor flows out of this list. Add a plain-text multiline `AppData` column to Participation and RSVPs. Enable unique values on each list's existing Title column so concurrent or retried creates cannot duplicate projections. Keep the two lists restricted to ministry leaders and the sync identity.
2. In each real Couples item, add `branch` and `members` to the existing `AppData` JSON. Each member needs `objectId` from the church tenant and a display `name`. Use unique identities, the existing `journalItemId`, and a journal folder scoped to those spouses. Keep the roster and all other live records in SharePoint.
3. Build the timer-only Azure Functions ZIP with `sh scripts/package-pilot-sync.sh /absolute/path/to/pilot-sync.zip`. Deploy it to a dedicated Node.js 22 Function App with a managed identity. The timer runs every five minutes at minute 4, 9, and so on through 59, which includes 11:59 p.m. Eastern. A later invocation can release a note if an earlier invocation failed. The host must supply the Azure App Service managed-identity endpoint and header. Assign its managed identity Microsoft Graph application `Sites.Selected` and write access to the RCI Marriage site only. Set `RCI_SITE_ID` to the Graph site ID. Keep app-only permission off the browser registration. The job requires read access to private intake and write access to the output lists and journals.
4. For sealed notes, generate a dedicated RSA key pair of at least 2048 bits in a private environment. Store the PEM private key in a protected secret store and expose it to the job as `RCI_SEALED_PRIVATE_KEY`. Publish only the RSA public JWK in a Monthly Content record. Its AppData needs `kind: "sealed-release"`, `season: "2027"` and `publicKey` (the JWK object). Releases occur at 11:59 p.m. Eastern on the last day of each month in 2027. Keep the private key and release configuration under the ministry's control. Test the key pair before accepting submissions. Changing the key mid-season can strand existing notes.
5. Publish two Monthly Content records with `kind: "event"`, `season: "2027"`, `event` equal to `retreat` or `harvest`, and `text` containing approved date, time, location and RSVP details. Each spouse can update their own response. Leader records identify the couple and spouse by roster IDs.
6. Verify in the tenant with a test couple and a leader-only account before publishing the app change. Check that both spouses can update the shared goals, each sees only their own intake, the leader sees weekly flags, and no note is published before release. Use a disposable pilot configuration and key for a timed release rehearsal. Confirm the worker runs successfully after the release time and both spouses see the two notes. Check that a spouse outside the test couple cannot open that folder.

Participation weeks run Monday through Sunday in Eastern time. A month fills in when either spouse answers a prompt or checks in during that month. The sync uses SharePoint author and creation metadata for these projections. It keeps a separate status row per spouse and week. Private answer or check-in text never goes into Participation or RSVPs. RSVP and sealed-note intake use the separate author-only Pilot Intake list. Existing prompt and check-in flows retain their current sources.

Notes open for submission January 29 Eastern. The browser encrypts each note with a one-time AES key wrapped with the published RSA public key. The job checks its own clock against the month-end schedule before decrypting eligible notes into the permissioned couple journal. The first eligible submission per spouse per month is used. February through December open on the first day of each month. Regular reveal workflows must explicitly filter for ordinary prompt answers. Site owners retain administrative access to journal entries after release. Anyone who can access the release private key can decrypt sealed intake, so restrict it to the private job. Journal changes use conditional writes to preserve concurrent edits. Failed runs should alert the ministry operator and be retried.

No client secrets, release keys, keyed flow URLs, or real couple records belong in Git.
